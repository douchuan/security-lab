# Security Lab Lesson 01

## 你的应用正在裸奔

**建议时长：60 分钟**

---

# 一、课程定位

这一节不是教大家“怎么启动 Docker”。

Docker、Docker Compose、Juice Shop 都只是我们今天使用的工具。

真正要学习的是一个问题：

> **如果你今天成为一家公司的 CISO，你会如何判断这家公司到底安不安全？**

这一节结束的时候，希望大家能够理解四件事情：

1. 什么是 **Attack Surface / 攻击面**
2. 为什么一个正常运行的 Web 应用，依然可能处于非常危险的状态
3. 为什么“有漏洞”和“正在被攻击”是两个不同的问题
4. 为什么企业安全不能只靠开发人员修漏洞，而需要一个完整的安全防御体系

最重要的是建立一个思维方式：

> **不要从“我们有什么安全工具”开始思考。**
>
> **要从“攻击者能怎么攻击我们”开始思考。**

---

# 二、0～5 分钟：你刚刚成为公司的 CISO

### PPT：封面

大家好，欢迎来到 Security Lab。

今天我们不把自己当成学生。

从现在开始，假设发生了一件事情：

---

**今天早上 9 点，你刚刚被任命为一家公司的 CISO。**

你坐进办公室。

CEO 找到你。

他说：

> “我们公司的系统安全吗？”

你会怎么回答？

---

很多人第一反应可能是：

“应该安全吧。”

但是作为 CISO，你不能这么回答。

因为“应该安全”不是一个安全结论。

你需要有证据。

所以 CEO 接着问：

> “如果现在有人正在攻击我们的系统，你知道吗？”

这时候，如果你没有 WAF、没有 IDS、没有 SIEM、没有主机监控，你可能只能回答：

> **“我不知道。”**

CEO 再问：

> “如果攻击者已经进入服务器，我们知道吗？”

还是：

> **“我不知道。”**

最后 CEO 问：

> “那你告诉我，我们到底哪里存在风险？”

如果你连公司的系统有哪些入口都不知道，那么你甚至没有开始做安全。

所以今天我们的第一个任务非常简单：

> **站在攻击者的角度，看一遍我们自己的系统。**

---

# 三、5～10 分钟：六次课之后，我们要建立什么？

### PPT：课程概览

整个 Security Lab 不是六个互相独立的技术实验。

它其实是在模拟：

> **一个 CISO 从零开始建立企业安全防御体系的过程。**

六节课，我们会不断遇到新的问题。

---

第一天：

> **我们的系统到底暴露了什么？**

所以今天先建立业务系统。

---

第二天：

> **有人正在攻击我们的 Web，怎么办？**

于是我们加入 WAF。

---

第三天：

> **攻击者甚至还没有攻击 Web，他正在扫描我们的网络。**

于是我们加入 NIDS，也就是 Suricata。

---

第四天：

> **如果攻击者已经进入服务器呢？**

网络设备可能不知道。

于是我们在主机内部部署 Wazuh Agent。

---

第五天：

> **如果每天有几万条安全事件怎么办？**

我们需要 SIEM，对这些事件进行分析和关联。

---

第六天：

> **CEO 不想看几万条日志，他只想知道现在到底发生了什么。**

所以最后我们建立 Dashboard 和态势感知。

---

大家注意这个变化。

我们不是：

> Lesson 1 学 Juice Shop
> Lesson 2 学 ModSecurity
> Lesson 3 学 Suricata
> Lesson 4 学 Wazuh

这样学完以后，很容易只记住几个产品名字。

我们真正要建立的是：

```text
攻击者
   ↓
攻击面
   ↓
防御
   ↓
检测
   ↓
分析
   ↓
告警
   ↓
态势感知
```

这才是整个课程的主线。

# 四、10～15 分钟：先理解整个安全体系

### PPT：技术架构

现在大家看一下最终我们要建立的体系。

```text
                         攻击者
                            │
                            ▼
                     ┌─────────────┐
                     │  Firewall   │
                     └──────┬──────┘
                            │
                            ▼
                     ┌─────────────┐
                     │     WAF     │
                     └──────┬──────┘
                            │
                            ▼
                     ┌─────────────┐
                     │ Juice Shop  │
                     └──────┬──────┘
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
       ┌─────────────┐             ┌─────────────┐
       │  Suricata   │             │   Wazuh     │
       │    NIDS     │             │    HIDS     │
       └──────┬──────┘             └──────┬──────┘
              └─────────────┬─────────────┘
                            ▼
                     ┌─────────────┐
                     │    SIEM     │
                     └──────┬──────┘
                            ▼
                     ┌─────────────┐
                     │  Dashboard  │
                     └─────────────┘
```

今天大家暂时不要试图记住所有东西。

我们只需要理解：

### Firewall

第一层。

主要解决：

> **谁可以进入我们的网络？**

它更多关注网络连接和访问控制。

---

### WAF

第二个概念。

解决：

> **这个 HTTP 请求是不是恶意的？**

比如：

```text
GET /search?q=' OR 1=1 --
```

这可能是 SQL Injection。

---

### Juice Shop

它不是安全产品。

它代表的是：

> **我们的业务。**

也就是说，真正需要保护的是业务应用。

---

### Suricata

它站在网络层。

主要观察：

> **网络上正在发生什么？**

比如端口扫描、攻击流量等等。

---

### Wazuh

它更加靠近主机。

观察：

> **服务器内部发生了什么？**

例如：

* 文件被修改
* 日志异常
* 主机状态变化

---

### SIEM

它解决另外一个问题：

> **这些安全事件放在一起，我们怎么看？**

---

### Dashboard

最后解决：

> **怎么让安全人员快速理解整个环境？**

所以你可以把它理解成：

```text
Firewall
    ↓
访问控制

WAF
    ↓
应用层防护

Suricata
    ↓
网络层检测

Wazuh
    ↓
主机层检测

SIEM
    ↓
事件分析

Dashboard
    ↓
态势感知
```

---

# 五、15～20 分钟：现在回到现实——Equifax

### PPT：Equifax 的教训

我们先讲一个真实世界的案例。

2017 年，Equifax 发生了一次非常严重的数据泄露事件。

攻击者利用了 Apache Struts 中的一个已知漏洞。

最终大约 **1.45 亿美国消费者**受到影响。

Equifax 后续与美国监管机构达成的和解金额最高达到 **7 亿美元**。

这里我想让大家注意的不是这个数字本身。

真正值得关注的是：

> **这是一个典型的企业安全体系失效案例。**

它不是简单的：

> “黑客太厉害了。”

而是涉及多个环节：

* 已知漏洞没有及时修复
* 资产和漏洞管理存在问题
* 攻击检测能力不足
* 数据保护存在问题
* 事件响应存在问题

所以作为 CISO，我们不能只问：

> “我们的代码有没有漏洞？”

还要问：

> “我们知道哪些资产存在漏洞吗？”

> “漏洞有没有及时修复？”

> “如果攻击者利用漏洞，我们能不能发现？”

> “如果已经入侵，我们能不能发现？”

> “如果已经发生数据泄露，我们能不能快速响应？”

这就是为什么企业安全是一套系统，而不是一个工具。

### PPT：当前架构——裸奔状态

现在我们不讨论 Equifax 了。

假设这就是一家公司的生产环境：

```text
Internet
    │
    ▼
Juice Shop
```

就这么简单。

没有 WAF。

没有 IDS。

没有主机监控。

没有 SIEM。

我们甚至没有建立完整的安全可见性。

大家想象一下：

你作为 CISO 第一天来到公司。

开发团队告诉你：

> “系统已经上线了。”

你打开浏览器。

网站能打开。

API 能访问。

页面也非常漂亮。

开发团队说：

> “没问题，系统运行正常。”

但是：

> **“系统运行正常”和“系统安全”完全是两回事。**

这是今天非常重要的第一个概念。

# 七、25～30 分钟：什么叫攻击面？

### PPT：攻击面

什么是 Attack Surface？

简单说：

> **攻击面，就是攻击者可以用来攻击我们的所有入口。**

比如一个 Web 应用可能有：

```text
Web 页面
API
登录接口
搜索接口
文件上传
管理后台
数据库
第三方服务
服务器端口
```

这些东西都可能成为攻击入口。

---

我们举一个生活中的例子。

假设你住的是一栋房子。

你有：

* 正门
* 后门
* 阳台
* 窗户
* 车库

如果只有正门开放，攻击者的入口比较少。

如果：

> 正门开着
> 后门开着
> 一楼窗户开着
> 车库门开着

那么攻击面就非常大。

网络系统也是一样。

---

所以：

> **Attack Surface 不是“漏洞数量”。**

这是两个不同概念。

例如：

一个系统可能有：

```text
100 个开放接口
```

这是攻击面。

其中：

```text
5 个接口存在 SQL Injection
```

这是漏洞。

攻击面告诉我们：

> **攻击者有哪些入口。**

漏洞告诉我们：

> **这些入口中哪些存在安全缺陷。**

---

# 八、30～35 分钟：Juice Shop 到底是什么？

### PPT：业务系统上线

现在介绍我们今天的实验对象：

**OWASP Juice Shop。**

大家不要把它理解成一个简单的“漏洞网站”。

它更适合被理解为：

> **一个模拟真实 Web 应用的安全靶场。**

里面故意设计了大量安全漏洞。

例如：

* SQL Injection
* XSS
* Broken Access Control
* IDOR
* JWT 相关问题
* 敏感信息泄露

为什么我们不直接拿一个真正的网站来攻击？

因为那是不负责任的。

安全实验必须：

> **在自己控制的环境里进行。**

所以我们使用 Juice Shop。

它给我们一个很好的环境：

```text
真实 Web 应用的感觉
        +
故意存在的安全问题
        +
我们完全控制的实验环境
```

这样我们可以放心地攻击。

---

# 九、35～40 分钟：为什么使用 Docker？

### PPT：Docker Compose

接下来大家可能会问：

为什么不用直接安装 Node.js？

为什么要用 Docker？

因为我们这个课程最终会变得越来越复杂。

今天只有：

```text
Juice Shop
```

下一节增加：

```text
Nginx
ModSecurity
Juice Shop
```

再下一节：

```text
Nginx
ModSecurity
Juice Shop
Suricata
```

再后面：

```text
Wazuh Agent
Wazuh Manager
OpenSearch
Dashboard
```

如果全部手工安装，实验环境很容易变成灾难。

不同同学：

* 操作系统不同
* 软件版本不同
* 配置不同
* 依赖不同

最后老师会发现：

> “为什么你的能跑，我的不能跑？”

所以 Docker Compose 在这里解决的是：

> **实验环境标准化。**

我们希望做到：

```text
git clone
     ↓
cd lesson-01
     ↓
docker compose up
     ↓
所有人得到基本一致的实验环境
```

---

这里还有一个非常重要的概念：

> **Docker 不等于安全。**

Docker 只是让我们更方便地建立和隔离实验环境。

不要因为应用放进 Docker，就认为：

> “它安全了。”

容器仍然可能存在：

* 网络暴露
* 权限问题
* 镜像漏洞
* 配置错误
* Secret 泄露

所以：

> **容器是部署技术，不是自动生成的安全边界。**

# 十、40～45 分钟：第一次启动系统

### PPT：动手验证

现在我们开始动手。

进入：

```bash
cd lesson-01
```

启动：

```bash
docker compose up -d
```

然后：

```bash
docker compose ps
```

这里我建议大家先不要急着打开浏览器。

我们先问一个问题：

> **“作为 CISO，我如何证明系统真的运行起来了？”**

所以我们查看容器状态。

然后：

```bash
docker compose logs
```

看看应用日志。

最后：

```bash
curl http://localhost:3000/rest/products
```

如果能够返回 JSON 数据，就说明：

> Web 应用已经可以通过 API 被访问。

---

这里可以停下来问学生：

### 问题

> 如果这是生产环境，你觉得把这个 API 直接暴露给互联网安全吗？

不要急着回答。

让大家先思考。

# 十一、45～50 分钟：真正的攻击开始

### PPT：动手验证 / attack.sh

现在我们执行：

```bash
bash attack.sh
```

这个脚本的意义不是：

> “老师给大家准备了一个脚本，大家运行一下。”

而是：

> **模拟攻击者对刚上线系统进行最基本的侦察和攻击。**

---

第一步：

### 应用正常响应

这说明：

> 系统工作正常。

但是：

**系统工作正常 ≠ 系统安全。**

---

第二步：

### 公开 API

我们发现：

> API 可以被直接访问。

这里大家应该开始产生一个疑问：

> “是不是所有 API 都应该公开？”

这就是安全问题。

---

第三步：

### SQL Injection

我们尝试一个恶意输入。

例如：

```text
' OR 1=1 --
```

这里大家不需要记住 SQL Injection 的所有细节。

今天只需要理解：

> **攻击者正在尝试改变服务器原本的 SQL 查询逻辑。**

---

最重要的现象来了：

> **请求直接到达了后端。**

没有 WAF。

没有规则拦截。

没有独立的网络检测层。

没有 SIEM。

所以我们甚至可能：

> **攻击已经发生了，但安全团队完全不知道。**

---

# 十二、50～54 分钟：CISO 现场做安全审计

### PPT：CISO 观察记录

现在我们把刚才的实验结果整理一下。

| 检查项    | 当前状态 |
| ------ | ---- |
| 应用可以访问 | ✅    |
| WAF    | ❌    |
| 入侵检测   | ❌    |
| 主机监控   | ❌    |
| SIEM   | ❌    |
| 安全态势感知 | ❌    |

大家注意一个非常有意思的地方。

我们的：

> **应用是绿色的。**

它可以启动。

API 可以返回数据。

用户可以访问。

但是：

> **安全体系是红色的。**

---

这其实就是企业里非常常见的情况。

开发团队说：

> “服务没问题。”

运维团队说：

> “机器没问题。”

但是 CISO 问的是：

> **“如果有人攻击它呢？”**

这是完全不同的问题。

# 十三、54～57 分钟：今天真正发现的是什么？

### PPT：攻击面

现在我们重新回到 Attack Surface。

今天我们其实没有解决任何漏洞。

我们只是发现：

> **我们的系统暴露了哪些入口。**

这非常重要。

因为安全工作的第一步不是：

> “安装一个安全产品。”

而是：

> **Asset Discovery / 资产发现。**

先回答：

```text
我有什么资产？
        ↓
哪些资产暴露在外？
        ↓
哪些服务可以访问？
        ↓
哪些入口存在风险？
        ↓
哪些攻击能够被发现？
        ↓
哪些攻击能够被阻断？
```

这才是安全工程的基本思路。

# 十四、57～60 分钟：留下一个问题

### PPT：下一课

最后不要直接说：

> “今天课程结束，下节课学习 WAF。”

这样会把故事重新变成工具教学。

应该这样结束：

---

今天你作为 CISO，发现了一个问题。

公司的 Web 应用已经上线。

攻击者可以直接访问。

甚至可以尝试 SQL Injection。

而现在：

> **没有任何东西站在攻击者和应用之间。**

所以你回到办公室。

CEO 又来问你：

> “你不是说我们的系统安全吗？”

你现在知道应该怎么回答了。

你会说：

> **“现在还不能这么说。”**

CEO：

> “那你准备怎么办？”

你回答：

> **“第一步，我要在 Web 应用前面增加一道防线。”**

---

下一节，我们要解决的就是这个问题：

# **如果攻击者正在攻击我们的 Web，我们能不能在请求到达应用之前，把它拦下来？**

这就是：

> **WAF。**

下一节，我们会把：

```text
Internet
   ↓
Juice Shop
```

变成：

```text
Internet
   ↓
Nginx + ModSecurity
   ↓
Juice Shop
```

然后我们亲手发起：

```text
SQL Injection
XSS
```

看看我们的第一道防线到底能不能挡住攻击。

# 教师提示

这一课有一个很重要的教学原则：

## 不要过早陷入工具细节

例如不要花 10 分钟解释：

* Dockerfile 怎么写
* Juice Shop 是什么技术栈
* Node.js 怎么运行
* Docker Network 的所有参数

这些内容可以在实验过程中简单说明。

这一课最重要的是让学生形成一个认知：
