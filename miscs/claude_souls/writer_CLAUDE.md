# CLAUDE.md — 网络安全实践教材

## 1. 项目简介

本项目是一个面向实习生的网络安全实践教学项目，使用 Docker Compose 和开源安全工具，通过六次课程逐步建立基础安全防御体系的认知与实践能力。

课程以 CISO（首席信息安全官）的视角审视企业资产保护问题，以 CISSP 所体现的安全管理与体系化思维为指导，结合真实可观察的实验结果，帮助学员理解安全控制的作用、实现方式、检测证据及其能力边界。

项目的目标不是安装和展示尽可能多的安全工具，而是让学员理解：

- 我们在保护什么资产？
- 资产面临什么风险？
- 不同安全控制分别解决什么问题？
- 如何验证安全控制是否生效？
- 如何从日志和告警中识别有意义的安全事件？
- 如何利用证据开展初步调查？
- 为什么没有告警不代表没有攻击？
- 如何理解单一安全工具的局限，以及不同安全控制之间的关系？

最终希望学员不仅知道如何操作工具，还能够解释为什么这样做、如何判断实验结果，以及不能根据现有证据得出什么结论。

## 2. 本次项目的核心任务

本项目采用明确的两阶段交付流程。

**第一阶段：编写六章《网络安全实践教材》。**

**第二阶段：基于已经完成的教材，提炼六次课的课堂 PPT。**

第一阶段是当前工作的首要目标。教材是本项目的主要知识载体，PPT 是后续从教材提炼出来的课堂材料。

当前阶段应优先提高理论深度、技术准确性、实验可复现性和章节连贯性，而不是优化幻灯片的页面布局或追求单页内容简洁。

课程的总体宗旨和六章划分已经确定。本次工作应在既有体系上打磨内容，不应无理由推倒重来，也不应为了扩充内容而随意增加课程或安全工具。

- 了解实验的网络结构、组件职责和数据流。
- 验证关键实验是否能够支持教材中的技术结论。
- 发现问题时，区分文档错误、实验配置错误、环境问题和检测机制的限制。
- 如果需要修改实验实现，应有明确的教学或技术理由，并尽可能进行实际验证。

不要编造不存在的实验功能、脚本、配置或成功结果。

如果发现某个核心原理无法通过现有实验充分验证，可以考虑扩展相应实验，但必须先判断是否确有必要，并控制额外复杂度。

教材应具有完整的书籍阅读体验，而不是简单地将现有 PPT 逐页扩写。

如果 `tutorials/` 中已经存在草稿或其他材料，应先检查并在原有基础上改进，避免覆盖已有工作或创建重复的教材体系。

教材中的实验步骤、命令和配置应尽可能与 `lesson-*` 中的实际实现保持一致。

该目录存放现有课堂讲义，是教材编写的重要参考资料。

应检查六次课现有讲义，理解其教学目标、知识结构、实验安排、架构图、日志示例和总结。

但讲义不是最终教材的结构模板。应在充分理解现有内容后，对其进行必要的补充、深化、纠错和重新组织。

如果讲义中的技术描述与实际实验不一致，应调查原因，并根据可验证的事实修正内容，而不是机械照搬。

第二阶段再基于最终教材提炼和更新 PPT，遵循项目已有的格式、工具和命名约定。

不要为了让三类材料表面一致而掩盖实际问题。

## 4. 课程宗旨与教学原则

### 4.1 以 CISO 的问题组织课程

课程围绕一个贯穿始终的问题展开：

> 如果你刚刚成为一家企业的 CISO，CEO 问你：“我们的系统安全吗？如果有人正在攻击我们，我们能发现吗？”你应该如何理解这个问题，并逐步建立基本的防御与检测能力？

每章都应回答一个具体问题，并与前后章节形成自然的学习路径。

### 4.2 理论服务于理解

本课程不是纯理论课，也不是照着命令执行的操作手册。

理论应当帮助学员解释实验现象、理解安全控制的工作方式，并判断实验结论是否成立。

对于必要的概念、架构、数据流和技术原理，应提供充分解释，不要为了追求简洁而删掉关键知识。

同时，不要为了展示专业性而堆砌与本章目标无关的概念。

### 4.3 证据优先

关键安全结论应尽可能由真实的实验结果、日志、告警、请求响应或配置证据支持。

工具成功启动不代表安全控制有效；出现日志不代表已经识别安全事件；产生告警也不代表已经确认入侵。

教材必须解释证据的来源、含义及局限。

### 4.4 明确能力边界

安全控制都有适用范围和前置条件。

教材应帮助学员理解：

- 未发现攻击不等于没有攻击。
- 没有告警可能与流量不可见、日志未采集、解析失败或规则未触发有关。
- 文件变化、端口扫描或登录失败等单一现象，不足以独立证明系统遭到入侵。
- 不同安全工具解决不同问题，不能将单一工具视为完整的安全体系。

### 4.5 注重工程实践

命令、配置和实验应尽可能准确、可复现。

涉及操作系统、容器网络、虚拟机、权限、软件版本或特定配置的内容，应说明相关前提。

无法实际验证的内容必须如实标注，不得虚构执行结果。

### 4.6 控制课程范围

课程建立的是基础安全防御体系的认知和实践能力，不是对完整企业安全体系的覆盖。

不要无必要地增加工具、扩大环境复杂度，或将未来规划写成已经实现的能力。

## 5. 六章教材的固定定位

六章的总体划分已经确定。应优先打磨各章的理论、实验和讲解质量，而不是重新设计课程体系。

| 章节 | 核心问题 | 主要内容 | 学习目标 |
|---|---|---|---|
| 第一章 | 暴露的应用有什么风险？ | Juice Shop、资产暴露、基础风险识别 | 理解资产、威胁、漏洞、风险与影响之间的关系 |
| 第二章 | 能否在请求到达应用之前拦截部分攻击？ | Nginx、ModSecurity、OWASP CRS、SQL 注入实验 | 理解 WAF 的工作位置、检测与阻断机制及其局限 |
| 第三章 | 能否发现网络侦察行为？ | Suricata、Nmap、端口扫描检测 | 理解网络可见性、NIDS 的检测方式及端口扫描的意义 |
| 第四章 | 能否发现主机文件发生异常变化？ | Wazuh Agent、文件完整性监控（FIM） | 理解基线、文件变化检测、主机侧证据与误报可能 |
| 第五章 | 如何从大量日志中识别有意义的安全事件？ | Wazuh Manager、日志解析、规则匹配、暴力破解相关实验 | 理解日志采集、解析、检测和事件关联之间的区别 |
| 第六章 | 如何利用安全事件开展初步调查？ | Wazuh Dashboard、索引与检索、告警及日志分析 | 学会从实际告警定位证据并开展基础调查 |

各章可以补充理解实验所必需的背景知识，但新增内容必须服务于本章的核心问题。

## 6. 六章之间的知识递进

整体学习路径是：

**风险识别 → 防护控制 → 网络侧检测 → 主机侧检测 → 日志分析与事件识别 → 事件检索与初步调查**

这是教学顺序，不代表真实企业网络中的所有流量或事件都必须依次经过每个组件。

教材应准确表达不同安全控制之间的关系：

- WAF 主要面向 Web 请求及相关应用层攻击。
- NIDS 观察其能够获得的网络流量。
- HIDS 从主机侧采集日志或监控相关行为。
- 不同数据源可将相关日志或告警提供给分析系统。
- Wazuh Manager 根据实际配置进行日志分析、规则匹配和告警生成。
- 索引组件与 Dashboard 支持数据检索、展示和分析。

架构图和数据流图必须以仓库的实际实现为依据。

如果项目尚未部署防火墙，不要将防火墙画成已经实现的实验组件。可以在理论层面介绍防火墙的作用，但必须区分现有实现与未来扩展。

同样，不要假设所有日志都会自动流经上述所有组件。

## 7. 教材编写标准

### 7.1 写作定位

教材面向具备一定计算机基础、正在学习网络安全的实习生。

写作深度应达到实践技术书籍的要求，既不是简短的操作手册，也不是追求全面覆盖的学术专著。

**教材不受 PPT 页数、单页文字数量或课堂幻灯片简洁程度的限制。**

每章应根据知识的复杂程度和实验需要，提供充分、连贯的解释。

不要把现有 PPT 逐页扩写成章节，也不要为了让书稿看起来更厚而增加无关内容。

### 7.2 每章的推荐结构

根据章节实际内容灵活组织，不要求每章机械地使用完全相同的标题。

建议包括：

1. 本章要解决的安全问题。
2. 必要的背景知识与核心概念。
3. 安全控制的工作原理。
4. 相关架构、组件职责和数据流。
5. 实验环境及前置条件。
6. 分步骤的实验操作。
7. 结果观察、日志分析与证据解释。
8. 常见故障与排查方法。
9. 能力边界、误报、漏报或其他局限。
10. 本章总结与练习。

理论篇幅由理解难度和实验需要决定。不要为了保持统一篇幅而删减必要解释，也不要强行填充所有小节。

### 7.3 理论内容的要求

- 先解释问题，再介绍理论和工具。
- 先建立概念模型，再说明具体实现。
- 对关键术语给出清晰定义。
- 对容易混淆的概念进行明确区分。
- 复杂原理可使用架构图、流程图、表格和代码示例。
- 解释关键配置的含义及其影响，而不是只贴出配置文件。
- 说明不同组件的职责和数据流。
- 对适用条件、实现差异和版本相关行为作必要说明。
- 避免空泛的背景介绍、重复总结、无关术语堆砌和夸大的安全结论。

教材应使用自然、准确的技术语言。可以展开解释，但不应通过重复相同观点制造篇幅。

### 7.4 理论与实验必须形成闭环

每项核心实验应尽可能包含：

1. 实验目标。
2. 要验证的原理或假设。
3. 环境和前置条件。
4. 实际操作及关键配置。
5. 预期结果。
6. 应观察的日志、字段、响应或告警。
7. 结果的技术解释。
8. 失败时的排查方向。
9. 实验能够支持和不能支持的结论。

建议优先采用对照实验，例如：

- 正常请求与恶意请求。
- 被拦截的请求与被放行的请求。
- 可见的网络流量与不可见的流量。
- 监控范围内的文件变化与范围外的文件变化。
- 单次登录失败与连续失败尝试。
- 成功解析的日志与未按预期解析的日志。

通过改变一个明确条件并观察结果，帮助学员理解安全控制的实际机制。

如果某项实验只能证明工具成功启动，却无法验证本章的核心目标，应重新审视实验设计。

### 7.5 区分事实、示例和拓展

教材必须清楚区分：

- **实际实现**：仓库中确实存在并可以检查的脚本、配置或功能。
- **已验证行为**：已经通过实际执行或可靠测试确认的结果。
- **原理性示例**：用于解释通用机制，但不代表仓库已经实现。
- **拓展内容**：帮助读者继续学习，但不属于当前实验的必做部分。

不得把原理性示例写成当前项目的实际能力，也不得把未经执行的实验描述为已验证成功。

## 8. 各章的重点审查要求

### 第一章：风险识别与应用暴露

重点检查：

- 是否区分资产、威胁、漏洞、风险与影响。
- 是否区分应用可以访问与应用存在可被利用的漏洞。
- 是否利用 Juice Shop 的实际现象支撑风险讨论。
- 是否明确故意脆弱的实验应用与生产系统之间的区别。
- 是否自然引出后续防护与检测。

不要把发现一个漏洞直接等同于完整的风险评估。

### 第二章：WAF 与 Web 应用防护

重点检查：

- 是否区分 Nginx、ModSecurity 与 OWASP CRS 的职责。
- 请求经过代理、WAF 和应用的路径是否符合实际部署。
- SQL 注入实验是否能够对比正常请求和攻击请求。
- 是否可以从实际响应或日志中确认检测与拦截行为。
- 是否解释规则、误报、漏报和 WAF 的能力边界。

如果出现 HTTP 错误码，必须确认其来源，不能仅凭错误码断定请求是由 WAF 拦截的。

### 第三章：NIDS 与网络侦察检测

重点检查：

- 是否解释 Nmap 扫描的目的及其与实际入侵的区别。
- 是否解释 Open、Closed、Filtered 等端口状态。
- 是否说明 Suricata 必须获得相关流量才能检测对应行为。
- 是否根据实际环境说明容器、虚拟机、宿主机与传感器之间的网络关系。
- 是否通过真实流量或告警验证检测结果。
- 是否区分网络不可见、规则未匹配和未产生告警等情况。

不得把端口扫描告警直接解释为系统已经遭到攻陷。

### 第四章：HIDS 与文件完整性监控

重点检查：

- 是否解释 FIM 的监控对象、基线与文件变化检测机制。
- 是否明确哪些目录和文件处于实际监控范围内。
- 是否通过修改受监控文件验证检测能力。
- 是否能够区分监控配置、事件采集和规则分析方面的问题。
- 是否明确文件修改告警本身不能证明恶意行为。

条件允许时，可增加监控范围内外的对照实验。

### 第五章：日志解析、检测规则与安全事件

本章是需要重点打磨的技术章节。

应根据实际实现，清楚区分：

1. 日志产生。
2. 日志采集。
3. 日志预处理与解析。
4. 规则匹配与检测。
5. 告警生成。
6. 必要时的事件关联或进一步分析。

重点检查：

- Decoder 与 Rule 的职责是否解释准确。
- 是否说明采集到日志不等于日志已经正确解析。
- 是否说明解析成功不等于一定会生成告警。
- 是否解释规则条件、阈值和时间窗口（如果实际实验涉及）。
- 是否区分单次登录失败与连续失败尝试。
- 是否确认日志来自所声称的登录场景。
- 自定义 Decoder、Rule 等配置是否符合实际语法并经过测试。

如果使用 SSH 登录日志，应明确这是 SSH 认证场景；如果使用 Web 登录日志，应明确其来源及解析机制，不要混淆两者。

适用时，应利用 `wazuh-logtest` 等实际工具验证日志解析和规则匹配结果。

不得将只适用于某种日志格式或特定条件的规则描述成通用的暴力破解检测机制。

### 第六章：安全事件检索与初步调查

重点检查：

- 是否准确区分日志采集、事件检测、索引存储、检索与可视化。
- 是否确认实际数据经过预期的数据路径进入 Dashboard。
- 是否能够从真实告警定位事件时间、来源、关键字段和相关证据。
- 是否解释告警与已确认安全事件之间的区别。
- 是否完成至少一次有意义的初步调查，而不只是展示 Dashboard 页面。

不得将 Dashboard 本身描述成完整的 SIEM，也不得声称未配置的数据源、原始日志存档或关联规则已经实现。

## 9. 技术验证与资料来源

### 9.1 技术验证

对于教材中的关键技术描述，应尽可能通过实际检查验证。

检查范围包括：

- Docker Compose 配置与服务依赖。
- 容器网络、端口映射和监听地址。
- 配置文件语法及挂载路径。
- 日志来源和实际格式。
- Decoder、Rule 及字段提取结果。
- 告警触发条件和实际输出。
- Dashboard 查询字段和实际数据。
- 命令参数、权限与运行环境。
- 清理实验环境后重新执行的可行性。

如果无法执行某项实验，应说明原因。静态检查不能被描述为完整的运行验证。

对可能破坏数据或影响宿主机的命令，应优先在隔离实验环境中执行。

### 9.2 参考资料

必要时可参考以下资料：

- NIST Cybersecurity Framework 2.0。
- CISSP 中与资产保护、风险管理、纵深防御、访问控制、监控和事件响应有关的基本思想。
- OWASP 的 Web 应用安全资料。
- Suricata、Wazuh、ModSecurity 和 OWASP CRS 的官方文档。
- MITRE ATT&CK 中与本课程实验直接相关的技术分类。

使用资料时：

- 优先采用官方文档和权威来源。
- 对版本敏感的功能核对对应版本的文档。
- 将引用的框架与当前问题联系起来，而不是机械罗列框架名称。
- 不要声称课程完整覆盖 NIST CSF 或 CISSP。
- 不要将教学简化模型误写成标准定义。
- 对尚不能确认的技术结论，记录为待验证项。

## 10. 第一阶段执行流程：完成教材

第一阶段是当前最高优先级的工作。

### 阶段一：仓库盘点

检查真实目录、现有文档、六个实验目录、`tutorials/` 和 `presentation/`。

了解现有材料及其依赖关系，不要只看 README 就开始重写。

### 阶段二：整体审查

逐课检查现有内容，识别技术错误、理论缺口、实验问题、重复内容和跨课程的不一致。

建立问题清单，并按以下优先级排序：

- **P0：必须修复。** 技术错误、错误的安全结论、关键实验不可执行或无法实现课程目标。
- **P1：应当改进。** 理论解释不足、实验证据不充分、重要概念混淆或知识递进不合理。
- **P2：可选优化。** 非关键的表达、版式、重复内容或拓展建议。

### 阶段三：制定教材大纲

在 `tutorials/` 中规划六章教材的目录。

明确每章的目标、核心问题、必要理论、实验、证据和学习成果，并检查章节之间是否重复或存在知识缺口。

先完成大纲和现有材料映射，再开始大规模编写正文。

### 阶段四：修复关键技术问题

优先处理会影响技术正确性、实验可复现性和核心结论的问题。

修复时尽量控制变更范围，并验证实验行为。

### 阶段五：逐章编写教材

在 `tutorials/` 中完成六章正文。

每章应具有完整的解释和实践闭环。不要将内容压缩成 PPT 式提纲，也不要只列出操作步骤而缺乏原理说明。

### 阶段六：全书审校

检查：

- 六章之间的术语是否一致。
- 架构图和数据流是否与实际实现相符。
- 同一技术概念是否出现相互矛盾的解释。
- 实验是否能够支持相关结论。
- 是否明确标记未验证内容与能力边界。
- 是否存在不必要的重复和偏离主题的内容。

### 阶段七：第一阶段验收

交付六章教材正文、全书目录、关键实验验证记录、技术审校报告及剩余问题清单。

第一阶段不以 PPT 是否完成为验收条件。

## 11. 第二阶段执行流程：从教材提炼 PPT

只有在第一阶段完成并通过审查后，才进入第二阶段。

以 `tutorials/` 中的最终版教材为主要内容依据，为六次课分别提炼课堂 PPT。

要求：

- 保留每章的核心问题、关键概念、必要架构图和主要结论。
- 按课堂讲解顺序组织内容，而不是直接复制教材段落。
- 将复杂理论转化为适合课堂讲解的图示、流程和对比。
- 保留关键实验步骤、日志和能够支持结论的证据。
- 将完整配置、深入解释、故障排查和拓展阅读留在教材中。
- 保证 PPT 与教材的技术描述和结论一致。
- 不得为了简化表达而制造技术错误或夸大安全能力。

如果制作 PPT 时发现教材存在重要缺口，应先修订教材，再更新 PPT。

PPT 应遵循项目现有的组织方式和工具链，不要无理由更换整套技术栈。

## 12. 修改边界与工作方式

本项目的重点是教材内容质量和实践教学效果。

应当：

- 修正技术错误。
- 补充必要理论。
- 改进实验步骤、证据解释和故障排查。
- 统一关键术语和架构描述。
- 删除重复、偏题或没有教学价值的内容。
- 更新与实际实现不符的项目文档。

不应：

- 推倒重来设计六章课程。
- 为了展示专业性而增加大量新工具。
- 无必要地扩大实验环境复杂度。
- 把未来规划描述为已经实现的能力。
- 将教材写成纯理论文章或命令操作手册。
- 大规模重构与当前目标无关的代码。
- 无理由更换现有技术栈。
- 编造实验结果或未经验证的结论。
- 把个人风格偏好包装成技术事实。

如果发现必须调整课程结构的重大问题，应先说明证据、影响和最小调整方案。

修改前检查仓库状态，保留已有工作，不要覆盖未经审查的内容或删除现有实验材料。

## 14. 最终质量标准

最终成果应满足：

- 六章课程仍然服务于既定宗旨和目标学员。
- 每章都能回答一个明确的安全问题。
- 理论内容充分、准确，并与实验紧密结合。
- 关键实验具有清晰的目的、步骤、预期结果和证据解释。
- 教材中的命令、配置、架构和技术结论与实际实现一致。
- 重要结论有实验结果或可靠资料支持。
- 对前置条件、能力边界和未验证事项有明确说明。
- 六章之间具有连贯的知识递进，没有明显的概念矛盾。
- 学员不仅知道如何操作，还能解释原理、分析证据并审慎判断结果。

请始终遵循以下原则：

**用 CISO 的问题组织课程，用安全理论解释原理，用开源实验提供证据，用能力边界培养真正的安全思维。**

当前阶段，请优先完成《网络安全实践教材》，不要提前将主要精力转向 PPT 制作。
